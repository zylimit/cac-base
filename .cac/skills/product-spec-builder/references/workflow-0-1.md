[推进六步]
    1. **进场调研**：先 `WebSearch` 用户提及的行业与标杆竞品；第一轮顺带确认风险档位（自用 / 内部 / 对外涉钱涉合规）以锁定提问预算。用户只给一句话时，首问固定：「先不列功能清单——按真实过程讲一次：谁在什么场景下用它、当时最卡在哪一步、最后手里要拿到什么结果？」
    2. **夯实地基（维度 1–4）**：拉通现状故事、三类干系人（受益/买单/受损）、规则与例外、拍板人与既定约束，能用一段人话回放且用户点头后再往下走。
    3. **覆盖扫描与细节收敛（维度 5–13）**：按「影响 × 不确定度」只问会改变首版实现或验收的缺口；每轮给推荐答案。触达问题预算上限时做收敛审计：能给低风险默认的标 `[默认]`，非阻塞未决项填齐五格进「待定问题」表。
    4. **高风险深挖（可选）**：对外或涉钱涉合规项目，复述前从 `references/elicitation-menu.md` 挑 3–5 项供用户按需点选（最多跑 2 项）。
    5. **需求自检与静态闸**：对照 `references/spec-self-review.md` 自查 → 生成 `Product-Spec.md` 与 `Product-Spec-CHANGELOG.md` → 运行 `node .cac/scripts/predev-lint.mjs` 修至 0 error（若启用人读文档同步跑 `node .cac/scripts/readable-docs.mjs init` + `build`）。
    6. **案例复述签字门**：用用户的真实案例把上线后那次完整走一遍（含例外与失败恢复），列出 `[推断]` 与 `[待定]` 条数供挑错；挑不出错即完成签字。

[何时算够了（完成度三测试）]
    - **交接测试**：未参与对话的 `implementer` 拿到这份 Spec，能否不靠猜直接编码？
    - **边际测试**：再多问一题，答案会改变首版写什么代码吗？不会就立即停问。
    - **不对称原则**：错一处就会整片返工的地基/范围/权限/状态必问到底；以后随时便宜微调的边角样式标 `[默认]` 或入待定表放行。
