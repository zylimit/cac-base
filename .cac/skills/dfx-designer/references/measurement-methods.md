# 从业务损失推导质量指标与防假绿统计口径

制定 DFX 目标、定义成功率分母或评估恢复机制副作用时读取本参考。

## 1. 五层分离（严禁互相冒充）
1. **业务结果定义**：用户在规定条件下真正要拿到的结果（如「预约结果可准确核对」，而非仅仅「接口返回 HTTP 200」）。
2. **目标来源**：区分「用户/合同已确认承诺」「AI 候选建议（待拍板）」与「实测现状基线（带时间/环境/命令）」，绝不拿模板示例数字冒充已批准 SLA。
3. **设计保护机制**：负责模块采用的具体手段（幂等键、事务、熔断、队列）及其仍无法覆盖的残余盲区。
4. **采集语义（防分母造假）**：
   - **观察单位**：按「用户独立业务意图」还是「HTTP 请求尝试次数」计？自动重试不能把 1 次用户意图刷成 3 次成功样本。
   - **超时、取消与未知态**：严禁把超时未完成请求从分母中悄悄剔除以凑出漂亮的 99.9% 成功率；零样本时标「无样本不可计算」，绝不报 100%。
   - **采集点盲区**：服务端日志看不到到达网关前断掉的请求，第三方回执「已接收」不等于终端用户「已送达」。
5. **真实运行证据**：未运行写「未运行」，缺工具写「缺检查」，跑挂写「FAIL」，绝不用 SRE 错误预算借口豁免 `security / safety / privacy` 必过门禁。

## 2. 保护机制的跨属性反查
- **加缓存**：降延迟，但可能引入过期决策或跨租户越权缓存 → 必核隔离键与失效条件。
- **加自动重试**：提瞬态恢复率，但多层叠加会引发重试风暴与外部重复扣款 → 全链路只留 1 层有界重试并配幂等键。
- **加详细日志**：利排障，但易把手机号/Token/口令打进磁盘 → 必配脱敏规则与日志零 PII 核查。
